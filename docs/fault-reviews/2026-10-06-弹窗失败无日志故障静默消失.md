## 1. 问题描述

### 1.1 问题场景

托盘或快捷键触发 `trans-window open`，子进程因任何原因失败退出：目标窗口找不到、`--target` 参数非法、配置读不出来、面板无法放置到前台……

### 1.2 具体表现

- 面板没有出现，用户看不到任何提示；
- `winlog` 里只有 `started with ...` 一行，**没有失败原因**；
- 排查只能靠猜。本次 P0（面板被放到屏幕外）能定位，靠的是 `placeOver` 恰好记录了坐标；若失败发生在更早的环节，则完全无迹可查。

### 1.3 错误信息

**日志信息**（修复前的 `panel.log`，只有开头、没有结局）：

```
2026-10-05T17:47:18 started with ["...trans-window.exe" "open"], target ""
（若此处失败，进程退出，日志到此为止——没有任何"为什么"）
```

## 2. 临时解决方案（可选）

在有控制台的环境手动运行 `trans-window open` 看 stderr。仅开发者可用，用户不行。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 观察到的表象：本次 P0 排查时发现，除了 `placeOver` 的坐标日志外，弹窗路径的失败从不落盘。
2. 读 `cmd/trans-window/main.go` 的 `exit()`：失败只写 `fmt.Fprintln(os.Stderr, ...)`。
3. 对照拉起方式：守护进程用 `win32.SpawnQuietly(..., createNoWindow)` 启动 `trans-window`，**没有控制台，stderr 无处可去**；`winlog` 包的注释本身就写着"程序没有控制台时不得不说的话写到这里"，但 `exit()` 没有用它。
4. 最终定位：错误出口只考虑了"人在控制台前"的场景，漏了"被守护进程拉起"的场景。

### 3.2 直接原因

`cmd/trans-window/main.go` 的 `exit()` 只写 stderr，不写 `winlog`。

**相关代码位置**：`cmd/trans-window/main.go`（修复前约 60 行）

**关键代码片段**：

```go
// 修改前：只有控制台能看到
func exit(err error) {
    if err == nil {
        return
    }
    fmt.Fprintln(os.Stderr, "trans-window:", err)
    os.Exit(1)
}
```

### 3.3 根本原因

- **设计层面**："说错误"这件事有两个出口（stderr、winlog），但没有约定"两条都走"；`winlog` 的定位（没有控制台的程序的唯一出口）没有贯穿到所有失败路径。
- **开发层面**：`main()` 开头就 `winlog.Note("panel", "started with ...")`，说明作者知道这个程序可能"无人看见"，但只记了开始、没记结局。

### 3.4 为什么没有提前发现

- 代码审查阶段：`exit()` 被当作样板代码跳过。
- 测试阶段：失败路径的"可观察性"没有断言（测试只看返回值，不看日志）。
- 监控告警：失败本来就是"什么都没有"，恰恰因此更需要记录。

## 4. 解决方案

### 4.1 根本解决方案

**修改文件**：`cmd/trans-window/main.go`

**修改前**：

```go
func exit(err error) {
    if err == nil {
        return
    }
    fmt.Fprintln(os.Stderr, "trans-window:", err)
    os.Exit(1)
}
```

**修改后**：

```go
// exit ends the program over a failure. The words go to the standard error,
// which is a console when a person asked for this from one and nowhere at all
// when the daemon opened it; the log is what says it happened either way.
func exit(err error) {
    if err == nil {
        return
    }
    winlog.Note("panel", "gave up: %v", err)
    fmt.Fprintln(os.Stderr, "trans-window:", err)
    os.Exit(1)
}
```

**方案说明**：保留 stderr（控制台用户体验不变），同时补 `winlog`（守护进程拉起时唯一可查的痕迹）。没有改成"只写日志"或"弹窗报错"：弹窗自身可能就是失败的那个，弹错误框属于越权。

### 4.2 影响范围评估

- 所有失败路径统一多一行 `gave up: ...` 日志，成功路径不变；
- 对现有测试无影响（测试不断言日志内容）；
- 日志量增加仅在失败时发生。

## 5. 预防措施

### 5.1 代码层面

- [x] 约定：凡是"可能无人在场"的进程（守护进程、托盘、被拉起的弹窗），失败出口必须同时写 stderr 和 `winlog`；
- [ ] 评审清单补充：新增失败分支时问一句"这个错误用户/日志能看到吗"。

### 5.2 测试层面

- [ ] 对关键失败路径（目标窗口不存在、`--target` 非法）补断言：`exit` 后日志含 `gave up:`（需可注入日志目录，暂记为待办）。

### 5.3 监控层面

- [x] 排查口径：`%LOCALAPPDATA%\trans\panel.log` 中出现 `gave up:` 即为弹窗失败，配合前一行 `started with` 可还原命令行与目标。

### 5.4 流程/规范层面

- [ ] 与 `winlog` 的定位保持一致：新增"没有控制台的程序"时，先接 `winlog` 再写业务。

## 6. 经验总结（一句话）

> 无人在场的进程失败时必须留下痕迹——错误只写 stderr 等于没有错误，`winlog` 才是这类程序真正的出口。
