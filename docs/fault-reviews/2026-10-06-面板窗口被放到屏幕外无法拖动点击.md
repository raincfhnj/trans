## 1. 问题描述

### 1.1 问题场景

1. 启动 `trans-windowd`（带托盘图标），或先点击过一次托盘图标菜单；
2. 通过托盘菜单"Open panel"（或快捷键 `ctrl+alt+t`、`trans-window open`）打开面板；
3. 面板窗口出现：主体缩在屏幕左上角，窗口的其余部分超出屏幕外；标题栏在屏幕外所以拖不动，可见部分是终端画布所以点不了，整个窗口无法关闭。

设置窗口（`trans-window settings`）同样命中。用户只能从托盘菜单点"Close panel"才能关掉它。

### 1.2 具体表现

- 窗口固定在屏幕左上角，超出屏幕之外（实际坐标为负值）；
- 无法拖动（标题栏在屏幕外 / 弹窗本身无边框）；
- 无法点击（可见部分是 TUI 画布，不响应鼠标）；
- 即使窗口可见，`alt+enter` 把翻译结果会"粘贴进一个看不见的窗口"——真正的目标窗口收不到。

### 1.3 错误信息

**日志信息**（`%LOCALAPPDATA%\trans\panel.log`，关键行已标注）：

```

`%LOCALAPPDATA%\trans\windowd.log` 印证用户只能从托盘关掉它：

```

坐标核算（完全吻合）：目标是 136×39 的托盘窗口（0,0 起），面板 1075×381，

## 2. 临时解决方案（可选）

### 2.1 方案描述

用户侧只能：托盘菜单 → "Close panel" 关掉不可见的面板；重新打开前先点一下别的窗口让前台回到正常窗口。

### 2.2 止血效果

能关掉窗口，但下次从托盘打开依然复发，无法根治。

### 2.3 临时方案的局限

根因在窗口选择与放置两处代码里，用户侧无法绕过。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 观察到的表象：窗口在左上角、屏幕外、拖不动、点不了。第一反应是"窗口坐标算错了"，但无法稳定复现路径（有时又正常）。
2. 第一排查方向：读放置代码 `internal/win32/console_windows.go` 的 `fitToPane`。发现居中公式 `left = area.Left + (area.width()-present.width())/2` 在面板比目标窗口大时会产生**负坐标**，且全程没有任何"夹回屏幕内"的约束——这是一个必然缺陷，但还需要解释目标为什么会是 136×39 的小窗口。
3. 第二排查方向：查 `%LOCALAPPDATA%\trans\panel.log` 的放置日志（`placeOver` 本来就会记录 target/window/screen 三组坐标）。日志直接给出 `opening over 0x1066c "trans-tray"` 与 `target 0,0-136,39 window -469,-171-606,210`：**目标窗口就是托盘自己的隐藏窗口**，两个缺陷同时命中。
4. 第三排查方向：托盘窗口为什么会成为"前台窗口"？读 `internal/tray/tray_windows.go` 的 `showMenu`：弹菜单前调用 `SetForegroundWindow(state.window)`（Win32 弹出菜单的经典技巧，否则菜单关不掉），菜单关闭后**从未把键盘还回去**。于是 `GetForegroundWindow()` 此后一直返回这个 136×39 的隐藏窗口。
5. 第四排查方向：目标是怎么选出来的？`cmd/trans-window/main.go` 的 `popupWindow` 直接用 `win32.Foreground()`（"谁拿着键盘就是谁"），而同一个包里的 `Windows()`/`HostWindow()` 早就写明"可见 + 不小于 200×120 + 有标题才算一个人能指着的窗口"，唯独选目标这一步没用这条规则。
6. 最终定位：**两个独立缺陷叠加**——(a) 目标选择会挑中隐藏的辅助窗口；(b) 放置算法不保证窗口留在屏幕内。任何一个单独存在都不会出现"屏幕外不可操作"，叠加后就是本次故障。

### 3.2 直接原因

1. `cmd/trans-window/main.go` 的 `popupWindow()` 用 `win32.Foreground()` 选目标，把托盘隐藏窗口当成"面板要覆盖的窗口"；
2. `internal/win32/console_windows.go` 的 `fitToPane()` 只做居中、不夹取边界，136×39 的目标把 1075×381 的面板居中到负坐标。

**相关代码位置**：

- `internal/tray/tray_windows.go` `showMenu()`（借走前台不归还）
- `cmd/trans-window/main.go` `popupWindow()`（选目标）
- `internal/win32/console_windows.go` `fitToPane()`（放置）

**关键代码片段**：

```go
// internal/tray/tray_windows.go — showMenu：借走前台，之后从未归还
call(procSetForegroundWin, uintptr(state.window))     // 托盘隐藏窗口成为前台
chosen, _, _ := procTrackPopupMenu.Call(...)           // 菜单关闭后前台仍是它
call(procPostMessageW, uintptr(state.window), wmNull, 0, 0)
if chosen != 0 { state.chose(Item(chosen)) }           // 于是子进程 Foreground() 拿到托盘窗口
```

```go
// cmd/trans-window/main.go — popupWindow：谁拿键盘就是谁，辅助窗口也算
window := win32.Foreground()
```

```go
// internal/win32/console_windows.go — fitToPane：只居中，不夹取
left := area.Left + (area.width()-present.width())/2   // 136-1075 → -469
top := area.Top + (area.height()-present.height())/2   // 39-381 → -171
call(procSetWindowPos, host, hwndTopMost, uintptr(left), uintptr(top), ...)
```

### 3.3 根本原因

- **设计层面**："窗口在最前面"被当成了"用户正在工作的窗口"，两者之间缺少一个"这窗口配当面板的落点吗"的判据。同一个包里 `Windows()` 早已定义了这条判据（可见、≥200×120、有标题），但选目标的路径绕开了它。放置算法也只关心"相对目标在哪"，从不关心"屏幕给得下吗"。
- **开发层面**：对 Win32 的借用式 API（`TrackPopupMenu` 必须先 `SetForegroundWindow`）只写了"为什么借"，没写"用完还"；窗口放置是纯算术本可以脱离桌面测试，却和 Win32 调用揉在一个函数里，完全没有测试。
- **流程层面**：弹窗定位属于"有桌面才能验证"的行为，现有测试全部绕开桌面（CI 的 Windows job 也只跑无窗口用例），放置正确性长期零覆盖。

### 3.4 为什么没有提前发现

- 代码审查阶段：审查集中在翻译/交付/剪贴板链路，没人把"目标窗口可能是个隐藏辅助窗口"当作输入来推演。
- 测试阶段：放置算术没有单元测试（它和 `SetWindowPos` 写在同一个函数里）；托盘菜单与前台窗口的交互无法在无桌面环境复现。
- 监控告警：`placeOver` 其实一直把 target/window/screen 三组坐标写进 `panel.log`，证据早就躺在日志里，只是没人回头读它——**日志有、看的人没有**，等价于没有监控。

## 4. 解决方案

### 4.1 根本解决方案

三层修复，任一层都能单独防止"窗口在屏幕外"：

**修复一：放置算法把窗口留在屏幕内**（`internal/win32/place.go` 新增，纯算术、任意平台可测）

```go
// 修改前（internal/win32/console_windows.go fitToPane）
left := area.Left + (area.width()-present.width())/2
top := area.Top + (area.height()-present.height())/2

// 修改后
left, top := placedWithin(present.width(), present.height(), area, workAreaNear(area))
```

`placedWithin` 在居中之后把左上角夹进"房间"（目标所在显示器的工作区，`MonitorFromRect`+`GetMonitorInfoW` 取得，含任务栏扣除与多显示器负坐标）；窗口比房间大时钉在近角。`internal/win32/place_test.go` 用本次故障的精确数字（136×39 的目标、1075×381 的面板）做回归。

**修复二：选目标只认"人能指着的窗口"**（`internal/win32/window_windows.go`）

```go
// 修改前
window := win32.Foreground()   // 谁拿键盘就是谁

// 修改后（cmd/trans-window/main.go popupWindow、internal/win32/selection_windows.go foregroundTarget）
window := win32.FrontPane()    // 前台是面板落点就用它，不是就沿 Z 序向下找第一个是的
```

`FrontPane` 用与 `Windows()` 同一条规则（`opensOver`：可见、≥200×120、有标题）挑面板落点，托盘隐藏窗口、任务栏等辅助窗口一律跳过；`OpenOver` 也用同一条规则拒绝非落点窗口（否则"完成的提示词会被粘贴进看不见的窗口"）。

**修复三：托盘用完键盘就还**（`internal/tray/tray_windows.go` `showMenu`）

```go
// 修改后：记住借走前的前台，菜单关掉后立刻还回去，再执行菜单选中的动作
lent := call(procGetForegroundWin)
call(procSetForegroundWin, uintptr(state.window))
chosen, _, _ := procTrackPopupMenu.Call(...)
call(procPostMessageW, uintptr(state.window), wmNull, 0, 0)
if lent != 0 && lent != uintptr(state.window) {
    call(procSetForegroundWin, lent)   // 先还键盘，再做菜单让做的事
}
```

**方案说明**：只做修复一，面板不再出屏幕但仍可能盖在错误窗口上（提示词还会粘贴进隐藏窗口）；只做修复二/三，任何一条将来被绕过（`--target` 显式指定、其他程序抢前台）仍会出屏。三层是"输入校验 + 位置兜底 + 根因消除"，缺一不可。没有采用"失败就报错退出"：面板哪怕落在错误位置也必须可关可拖（本次用户只能靠托盘关窗口就是教训）。

### 4.2 影响范围评估

- `internal/win32/place.go` / `place_test.go`：新增纯逻辑与测试，不影响现有行为以外的路径；
- `Windows()`/`HostWindow()` 的 200×120 判据统一成 `minPaneWidth/minPaneHeight` 常量，行为不变；
- `FrontPane()` 改变了 `popupWindow` 与划词捕获的目标解析：以前拿"任意前台"，现在拿"第一个落点窗口"，对正常场景（前台是浏览器/终端）结果一致；
- `OpenOver` 新增拒绝条件：显式 `--target` 指到一个小于 200×120 或不可见的窗口时会明确报错，而不再是默默盖上去；
- 托盘归还前台只影响菜单关闭瞬间，正常流程无感知；
- 兼容性：多显示器（负坐标）与缩放坐标系（日志中的虚拟坐标）都由 `placedWithin` 原样保留，不夹到 [0, screen]。

## 5. 预防措施

### 5.1 代码层面

- [ ] 任何窗口落点计算必须经过 `placedWithin`（居中 + 夹取工作区），禁止直接 `SetWindowPos` 传算出来的坐标；
- [ ] 任何"用户正在用的窗口"判定必须走 `FrontPane`（落点视角）或 `Foreground`（键盘视角），二者含义写进注释、不得混用；
- [ ] 借用 Win32 状态（前台、剪贴板、输入焦点）的代码必须在同函数内归还，评审时按"谁借谁还"检查。

### 5.2 测试层面

- [x] `internal/win32/place_test.go`：居中、屏幕边缘、比房间大、多显示器负坐标、本次故障的 136×39 目标（已补）；
- [x] `internal/win32/window_windows_test.go`：`FrontPane` 必须答出 `opensOver` 认可的窗口（已补）；
- [ ] 有条件时补一条带桌面的冒烟：`trans-window open --probe 500` 断言 `panel.log` 里 window 坐标非负且落在 screen 内。

### 5.3 监控层面

- [ ] `placeOver` 的日志已是完整证据（target/window/screen 三组坐标），约定：放置后 window 左上角必须 ≥0 且不超出 screen，越界即视为故障，读日志即可发现；
- [ ] 弹窗失败（`gave up: ...`）已进 `panel.log`，排查问题先看 `%LOCALAPPDATA%\trans\panel.log`。

### 5.4 流程/规范层面

- [ ] 复盘结论同步：Win32 图形相关的"纯算术部分"必须拆出无 build tag 的文件（本仓库已有 `match.go` 先例），否则永远无法在 CI 里被测到；
- [ ] 评审清单补充：凡 `GetForegroundWindow`/`SetForegroundWindow`/`TrackPopupMenu` 出现处，必须说明键盘的借用与归还。

## 6. 经验总结（一句话）

> 拿"谁在最前面"当"用户在哪个窗口工作"之前，先确认那不是一个隐藏的辅助窗口；而任何窗口坐标在写进 `SetWindowPos` 之前，必须先夹回屏幕的可用区域——居中公式天然会产生负坐标。
